# Backlog User Stories

Практична робота №5. User Stories та критерії приймання

Проєкт: консольна програма прогнозу погоди. Група ІПЗ-11, ЛНТУ

## 1. Формат User Story та приклад аналізу

User Story — це короткий опис функції з точки зору користувача. Формат: **«Як <роль>, я хочу <дія>, щоб <результат>»**.

Розбір на прикладі US-1 «Як користувач, я хочу ввести назву міста, щоб отримати прогноз погоди для нього»:

- **Роль:** користувач, тобто та, для кого робиться функція.
- **Очікувана дія:** ввести назву міста.
- **Очікуваний результат:** отримати прогноз погоди для цього міста.

Добра історія пояснює не тільки «що робити», а й «навіщо», і має перевірні критерії приймання. Критерії (Acceptance Criteria) записано у форматі **Дано / Коли / Тоді**: у якій ситуації, після якої дії і що має статися.

## 3. Критерії приймання

**US-1. Введення міста**

- Дано працюючий інтернет. Коли користувач вводить «Луцьк», тоді програма показує прогноз для міста Луцьк.
- Дано працюючий інтернет. Коли користувач вводить назву англійською (наприклад, Lviv), тоді програма знаходить місто й показує прогноз.

**US-2. Таблиця прогнозу**

- Дано знайдене місто. Коли програма отримала дані, тоді виводиться таблиця з рівно 5 рядків, перший з яких відповідає сьогоднішній даті.
- Дано виведену таблицю. Коли користувач її читає, тоді кожен рядок містить дату, мінімальну й максимальну температуру та опади у міліметрах з одним знаком після коми.

**US-3. Місто не знайдено**

- Дано назву, якої не існує («asdfgh»). Коли програма не знаходить місто, тоді вона виводить «Місто не знайдено.» і знову запитує місто.
- Дано порожній ввід (натиснуто Enter). Коли програма це помічає, тоді виводиться повідомлення про порожній ввід і програма знову питає місто.

**US-4. Помилки мережі**

- Дано вимкнений інтернет. Коли користувач вводить існуюче місто, тоді програма виводить повідомлення про помилку мережі й не завершується аварійно.
- Дано сервер, що не відповів за 10 секунд. Коли час очікування вичерпано, тоді програма виводить повідомлення про таймаут і знову питає місто.

**US-5. Кілька міст підряд**

- Дано виведений прогноз для одного міста. Коли вивід завершено, тоді програма знову запитує місто.
- Дано після першого запиту. Коли користувач вводить друге місто, тоді виводиться його прогноз без перезапуску програми.

**US-6. Історія запитів**

- Дано два успішні запити. Коли користувач вводить «історія», тоді програма показує обидва міста з датою й часом.
- Дано порожню історію. Коли користувач вводить «історія», тоді програма виводить «Історія порожня.»
- Дано запит з помилкою (невідоме місто, немає мережі). Коли програма зберігає історію, тоді такий запит у неї не потрапляє, а разом усіх записів не більше 10.

**US-7. Збереження історії між запусками**

- Дано виконаний запит і закриту програму. Коли користувач запускає її знову та вводить «історія», тоді бачить попередні запити.
- Дано відсутній або пошкоджений файл history.json. Коли програма запускається, тоді вона починає з порожньої історії без помилки.

**US-8. Вихід**

- Дано програму, що очікує назву міста. Коли користувач вводить «вихід» (у будь-якому регістрі), тоді програма виводить «До побачення!» і завершує роботу.

## 4. Перевірка на повноту та зрозумілість

Історії перевірено за критеріями **INVEST**: Independent (незалежна), Negotiable (обговорювана), Valuable (цінна), Estimable (оцінювана), Small (невелика), Testable (перевірна).

| ID | I | N | V | E | S | T | Зауваження |
| --- | --- | --- | --- | --- | --- | --- | --- |
| US-1 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | Базова історія, на неї опираються інші |
| US-2 | частково | ✓ | ✓ | ✓ | ✓ | ✓ | Потрібна US-1 (є дані для таблиці) |
| US-3 | частково | ✓ | ✓ | ✓ | ✓ | ✓ | Гілка помилки в сценарії US-1 |
| US-4 | частково | ✓ | ✓ | ✓ | ✓ | ✓ | Гілка помилки в сценарії US-1 |
| US-5 | частково | ✓ | ✓ | ✓ | ✓ | ✓ | Надбудовує US-1 |
| US-6 | частково | ✓ | ✓ | ✓ | ✓ | ✓ | Показує дані успішних запитів з US-1 |
| US-7 | частково | ✓ | ✓ | ✓ | ✓ | ✓ | Перевіряється через команду з US-6 |
| US-8 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | Незалежна дія |

Висновок: кожна історія має роль, дію та результат, містить перевірні критерії і виконується в межах однієї ітерації. Часткова залежність від US-1 цілком прийнятна: її враховано у порядку реалізації: спочатку Must, потім Should.
