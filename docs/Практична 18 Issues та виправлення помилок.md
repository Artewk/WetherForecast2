# Issues та виправлення помилок

Практична робота №18. Пошук, аналіз та виправлення помилок

Проєкт: консольна програма прогнозу погоди. Група ІПЗ-11, ЛНТУ

## 1. Як шукали помилки

Програма пройшла ручні тест-кейси (практична №15), тому звичайні сценарії працюють. Для пошуку проблем було перевірено нетипові ситуації, яких тест-кейси не покривали:

- робота з файлом історії у незвичних умовах (лише для читання, дані з порожнім записом);
- запуск різними способами (Visual Studio та команда dotnet run);
- поведінка програми при некоректному виборі у списку міст.

Усі проблеми нижче потрібно відтворити на власному комп’ютері перед створенням Issue і записати фактичний результат.

## 3. Опис проблем

### Проблема 1. Аварійне завершення, якщо файл історії лише для читання

**Пріоритет:** високий (програма вилітає з необробленим винятком після успішного прогнозу).

**Кроки відтворення:**

1. Запустити програму, зробити один успішний запит і вийти — створиться файл history.json у папці bin/Debug/net9.0.
2. У властивостях файлу history.json позначити «Тільки для читання».
3. Запустити програму і ввести «Луцьк».

**Очікуваний результат:** прогноз виводиться, програма повідомляє, що історію не збережено, і продовжує працювати.

**Фактичний результат:** після таблиці програма аварійно завершується з винятком UnauthorizedAccessException (потрібно підтвердити при відтворенні).

**Причина:** метод SaveHistory обробляє лише IOException, а один з винятків, що виникає при запису у файл лише для читання, це UnauthorizedAccessException.

**Виправлення:** у методі SaveHistory після блоку catch (IOException) додати:

```csharp
catch (UnauthorizedAccessException)
{
    Console.WriteLine("Немає доступу до файлу історії, історію не збережено.");
}
```

### Проблема 2. Файл історії створюється в різних місцях залежно від способу запуску

**Пріоритет:** середній (історія «зникає» при зміні способу запуску, і файл може потрапити в репозиторій).

**Кроки відтворення:**

1. Запустити програму з Visual Studio (Ctrl+F5), зробити запит, вийти — файл history.json з’являється у bin/Debug/net9.0.
2. Відкрити термінал у папці проєкту (де лежить Program.cs) і запустити команду dotnet run, зробити запит і ввести «історія».
3. Подивитися, де з’явився файл, і виконати git status.

**Очікуваний результат:** файл історії завжди знаходиться в одному місці, історія однакова незалежно від способу запуску, а git його не бачить.

**Фактичний результат:** при запуску через dotnet run у папці проєкту створюється окремий history.json поруч із Program.cs, історія в ньому не збігається з тією, що була при запуску з Visual Studio, і git status показує його як новий файл (потрібно підтвердити при відтворенні).

**Причина:** шлях до файлу задано як відносний («history.json»), тому він залежить від робочої папки програми.

**Виправлення:** у класі Program замінити рядок `const string HistoryFile = "history.json";` на:

```csharp
static string HistoryFile = Path.Combine(AppContext.BaseDirectory, "history.json");
```

Тоді файл завжди знаходиться поряд із виконуваним файлом програми (у папці bin), незалежно від способу запуску.

### Проблема 3. Команда «історія» аварійно завершує програму, якщо у файлі є порожній запис

**Пріоритет:** низький (ситуація малоймовірна, але доводить недостатню перевірку даних з файлу).

**Кроки відтворення:**

1. Закрити програму і замінити вміст файлу history.json на `[null]`.
2. Запустити програму і ввести «історія».

**Очікуваний результат:** «Історія порожня.»

**Фактичний результат:** програма аварійно завершується з винятком NullReferenceException (потрібно підтвердити при відтворенні).

**Причина:** JSON валідний, тому виняток не виникає і LoadHistory повертає список, у якому є порожній запис (null). Після цього ShowHistory звертається до властивостей «нічого».

**Виправлення:** у методі LoadHistory замінити рядок `return list;` на:

```csharp
List<HistoryEntry> clean = new List<HistoryEntry>();
for (int i = 0; i < list.Count; i++)
{
    if (list[i] != null)
    {
        clean.Add(list[i]);
    }
}

return clean;
```

### Проблема 4. Невірний номер при виборі міста мовчки замінюється першим

**Пріоритет:** низький (незручність для користувача, а не збій). Працює після злиття історії US-9.

**Кроки відтворення:**

1. Ввести «Springfield», щоб показався список міст.
2. У рядку «Оберіть номер» ввести 99.

**Очікуваний результат:** програма повідомляє, що номер невірний, і пояснює, яке місто вибрано.

**Фактичний результат:** програма без жодного повідомлення показує прогноз для першого міста, і користувач може не помітити, що отримав не те, що обирав.

**Виправлення:** у блоці вибору міста після блоку `if (int.TryParse(choice, out number) && ...) { ... }` додати:

```csharp
else if (choice != null && choice.Trim() != "")
{
    Console.WriteLine("Невірний номер, обрано перше місто.");
}
```

Порожній ввід (Enter) належить до нормальної поведінки (береться перше місто), тому повідомлення для нього не виводиться. Очікуваний результат тест-кейсу TC-16 також потрібно оновити.

## 5. Як оформити це на GitHub

1. **Створити Issues.** Репозиторій → вкладка Issues → New issue. Ввести назву та опис (кроки відтворення, очікуваний та фактичний результат, пріоритет), у полі Labels обрати bug або enhancement. Записати реальні номери створених Issue.
2. **Створити гілку** від master (наприклад, fix/bugs-18) і виправити кожну проблему окремим комітом, наприклад «Fix read-only history file crash».
3. **Створити Pull Request.** У описі написати кожне з ключових слів окремим рядком: «Closes #номер» (для кожного Issue). Після злиття GitHub сам закриє ці Issues.
4. **Злити PR**, потім у Visual Studio перейти на master і зробити Pull.
5. **Повторно перевірити** кожну проблему на оновленій версії й записати результат у таблицю вище.
6. **Для здачі:** скріншоти списку Issues (відкриті до виправлення і закриті після), одного Issue з посиланням на PR та повторного тестування.
